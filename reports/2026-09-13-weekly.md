## Day 1 — saved-order record from the real cart (`de404ca`, 2026-09-09)

The checkout handlers built the saved order record's item list from the local SQLite cart
instead of the real DoorDash cart just checked out — if the two had drifted (e.g. a
`REMOVE_ITEM` that only logged a warning), the recorded order wouldn't match what was
charged. `checkoutCurrentCart()` now scrapes the checkout page's itemized order list and
returns it; `server.js` builds the saved record from that when present, carrying each local
item's id/options/source by normalized name match so `[REORDER]` still works, falling back
to the local cart when the scrape is empty. 9 unit cases pass.

**Was unverified going in:** the checkout-page scrape itself — the Pi's browser can't load
DoorDash's checkout page. Rode with Day 4 below.

## Day 3 — SMS `[SELECT]` split-brain (`ed9247a`, 2026-09-09)

A second `[SELECT]` in one SMS session didn't update `prefs.currentRestaurant` — the SMS
handler only wrote it inside the menu-load success branch, while the cache-side
`cacheCurrentRestaurant()` only ran on the scrape-success path, so a failed 2nd select left
the two disagreeing and later adds landed on the wrong restaurant. Fixed to persist both
together the moment the selection resolves, before the menu load — mirrors the touchscreen
handler. Verified both fast-path and scrape-fail 2nd selects live via `/api/message`.

## Day 4 — pre-charge scrape verification: real blocker found and fixed, new one hit (2026-09-11 → 2026-09-13)

**2026-09-11:** deployed to Railway, drove a fresh SMS order toward the checkout-preview
step, and hit two new bugs instead of reaching it: `extractMenuItems()` returned 0 items for
every restaurant tried (Taco Bell, Tacos Los 3 Hermanos, Little Caesars — identical page
height across all three, suspicious), and Claude sometimes skipped the real `[SELECT]`
command on a retry and hallucinated a plausible-looking menu from training data instead.
Session paused before reaching a real checkout preview; nothing charged.

**2026-09-13 — root-caused and fixed the 0-items bug.** Added a targeted diagnostic dump to
`extractMenuItems()` for the specific case where prices are detected but extraction finds
nothing (`37ffe6d`), deployed, and reproduced immediately. The dump caught the real page
content: `document.title` was DoorDash's generic homepage title and the body was pure
logged-out marketing copy ("$0 DELIVERY FEE ON FIRST ORDER... Become a Dasher"), not the
store page — despite `page.url()` correctly showing the store URL. Traced to a race: the
SMS/voice restaurant-select handler fired `doordash.clearBrowserCart()` **unawaited**
immediately before `doordash.extractMenuItems()`. `clearBrowserCart()` is lock-serialized
against other locked browser operations, but `extractMenuItems()` is exported unlocked, so
it doesn't wait for `clearBrowserCart()`'s internal `page.goto('/home')` (needed to reach
the real cart drawer) — and sometimes ends up reading the homepage mid-navigation instead of
the store page. Explained every symptom exactly: identical page height (home is always the
same page), "prices detected" (from home's own promo banner), 0 real items.

Fixed by deferring `clearBrowserCart()` until after `extractMenuItems()` resolves (`057381c`).
**Verified live:** the exact restaurant that returned 0 items twice before the fix (Dave's
Hot Chicken) returned a real, correct 108-item menu immediately after, from a fresh select.
Checked every other `extractMenuItems()` call site — none had the same ordering bug.

**Confirmed the Claude-hallucination bug is broader than documented** — it fired on fresh
first-try selects today (3-for-3 on one test number: Pieology, Little Caesars, Taco Bell all
returned complete, correctly-priced fake menus with zero matching `[SELECT]` or extraction
log lines), not only on retries as the 9/11 write-up said. Makes SMS an unreliable test
harness on its own — real verification now needs either the kiosk API or a log check for an
actual `[SELECT]` line. Still open, needs a system-prompt fix.

**New finding:** a fresh search can resolve `[SELECT]` against a stale cached search-results
list — searching "dominos" and replying "1" resolved against a leftover cached Wingstop
search instead, landing on Dave's Hot Chicken. Not yet investigated.

**Reached the actual Day 4 deliverable and hit a new blocker.** Using the kiosk API

**Through-line: nothing has an edge, and that's the honest finding, not a failure.** SMA
doesn't beat buy-and-hold; the trained model is worse than a coin flip on the holdout; the
agent ensemble's apparent win over buy-and-hold on this holdout is explained by trading only
6.3% of the time on a below-chance rule agent (hit rate 0.455) during a bad stretch for BTC —
suppressing losses by barely trading, not finding signal.

**Phase 2** — bar-by-bar backtester: decisions on bar *t* fill at the next bar's open, costs
on by default, and a `MarketView` that structurally can't see past *t* (a lookahead
cheat-test confirms it). Baseline over full BTC-USD history: buy-and-hold +1958%/−77%
drawdown/Sharpe 0.95 vs. `sma_cross(20,50)` +1286%/−59%/Sharpe 1.00 — the SMA filter trades
return for a calmer ride, it doesn't add edge. Three real bugs found and fixed during a
deep math review: a silent `NaN` corrupting the portfolio, duplicate-timestamp rows
accepted, and Sharpe annualization not accounting for timeframe.

**Phase 3** — `HistGradientBoostingClassifier`, 13 right-bounded features, binary
next-bar-up label, rolling walk-forward, held-out ~20% scored once. **Holdout ROC-AUC 0.48
— below chance**, calibration inverted at the tails. As a strategy: −6.9%/−38% drawdown,
losing to buy-and-hold while churning fees. Correctly calls the Phase 6 real-money gate a
no-go on this evidence — the system telling the truth for $0.

**Phase 4** — an agent ensemble (`Vote` schema + a `ToolSandbox` every agent tool clips to
the current bar; an LLM math-expert agent restricted to numeric tools only, so it stays
honestly backtestable; a deterministic `NumericRuleAgent`; a consensus gate requiring
unanimous long + a confidence threshold; a crypto/news agent marked forward-only, not
backtestable). Evaluated against the real BTC holdout: ensemble +0.5%/−5.4%/Sharpe 0.10 vs.
buy-and-hold −4.3%/−53.1%/Sharpe 0.14 — beats it on return and drawdown, but the gate only
agreed to go long on 33 of 521 decision points (~94% cash) and the rule agent's own hit rate
on those was 0.455, below chance. Written up, tagged, pushed, CI green.
