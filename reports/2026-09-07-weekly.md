## Day 1 — stale-restaurant boot-prewarm hijack (`65739dd`, verified live)

The Day-5 smoke test the week before found that a restaurant left cached in the DB from an
old session could hijack a live, unrelated session: on boot the server fired
`prewarmRestaurantPage(cachedRestaurant.url)`, which — even though it holds the browser
lock — navigated the shared page away from the restaurant the user was actively ordering
from, mid-session, and reverted the persisted "current restaurant" back to the stale one.
The user's next add then ran against the wrong store and failed with "0 items found".

Fix: boot prewarm now calls `prewarmBrowser()` (homepage only, harmless) instead of
navigating to a specific stale store. `prewarmRestaurantPage()` also now self-locks and
captures a sequence number synchronously, so a superseded queued prewarm skips its
navigation entirely.

Verified: stale restaurant cached → restart → boot log shows homepage-only, no store nav;
a fresh order (search / select / add) then landed correctly with no hijack; real cart
confirmed empty.

## Day 2 — Little Caesars "Custom Stuffed Crust" required options (2026-09-01, verified live, uncommitted)

Build-your-own pizzas were surfacing only one generic option group ("Your recommended
options" = sauce amount) instead of the real required Sauce + Cheese groups, so cheese got
auto-defaulted server-side and the user never picked it.

The modal never opens via click for these items, so DOM extraction can't see the groups.
Going the GraphQL route instead surfaced **three real bugs**, all now fixed:

1. **`itemPage` GraphQL query was stale** — still sent the `isNested` argument, which
   DoorDash removed. Every call 400'd `GRAPHQL_VALIDATION_FAILED`, so the HTTP
   options fast-path had been **dead for every optioned item at every restaurant**,
   always silently falling back to Playwright DOM scraping.
2. **`extractStoreIdFromUrl` returned the menu id, not the store id** for canonical
   `/store/<slug>-<storeId>/<menuId>/` URLs — so item-id lookups always missed and
   `fetchItemPageViaAPI` 404'd.
3. **SSR-only stores expose no item id in the DOM or React fiber** — Little Caesars puts
   them only in DoorDash's server-streamed `__next_f` payload. Added a parser that pulls
   `{id, name}` pairs from that payload and stamps the real id onto the cached menu so it
   survives a restart.

Also: `convertOptionListsToRequired` now surfaces genuinely-required groups that DoorDash
ships as `isOptional:false / minNumOptions:0`, and discovery + payload-builder now use the
same rule so we don't add-then-fail on a group we never asked about.

Verified live against the real cart, twice — including once after a full restart with an
empty in-memory id cache, proving the persisted-id path — "Custom Stuffed Crust" with
Sauce=Regular + Cheese=Regular added via the HTTP API at the correct $17.49 base, no wrong
upcharge.

**Known rough edge (reported, left for later):** Costa Vida "Single Taco" add still fails —
DoorDash's `itemPage` response *omits* the required "Tortilla" group entirely, so the API
add is rejected and the Playwright fallback hits the pre-existing Costa Vida
menu-render flakiness. Never worked before this change either.
