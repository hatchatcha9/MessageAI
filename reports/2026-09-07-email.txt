DAY 1 - STALE-RESTAURANT BOOT-PREWARM HIJACK  (65739dd, verified live)

A restaurant left cached in the DB from an old session could hijack a live,
unrelated session: on boot the server navigated the shared browser page to
that stale restaurant, mid-session, and reverted the persisted "current
restaurant" to the old one - so the user's next add ran against the wrong
store and failed. Fix: boot prewarm now loads the homepage only. The
prewarm function also self-locks and sequence-guards so a superseded queued
prewarm skips its navigation.
Verified: stale restaurant cached, restart, boot goes homepage-only with no
store nav; a fresh order then landed correctly; real cart confirmed empty.

DAY 2 - LITTLE CAESARS REQUIRED OPTIONS  (604a267, verified live)

Build-your-own pizzas were surfacing only one generic option group instead of
the real required Sauce + Cheese groups, so cheese got auto-defaulted and the
user never picked it. Going the GraphQL route instead of the modal surfaced
THREE real bugs, all now fixed:

  1. The itemPage GraphQL query still sent an argument DoorDash removed -
     every call failed with a validation error, so the HTTP options fast-path
     had been DEAD for every optioned item at every restaurant, always
     falling back to slower DOM scraping.
  2. The store-id extractor returned the menu id, not the store id, for
     canonical URLs - so item-id lookups always missed.
  3. Some stores (Little Caesars) expose item ids only in the server-streamed
     page payload, not the DOM. Added a parser that also stamps the real id
     onto the cached menu so it survives a restart.

Verified live against the real cart, twice, including once after a full
restart with an empty id cache - "Custom Stuffed Crust" with Sauce=Regular +
Cheese=Regular added via the HTTP API at the correct $17.49 base.

Known rough edge (reported, not a regression): Costa Vida "Single Taco" add
still fails - DoorDash's itemPage response omits the required "Tortilla"
group entirely.


DAY 3 - SCRAPED NAME ARTIFACTS  (4be5269, verified live, done Sun Sep 7)

The DOM-scrape fallback could mangle names when a card's name wraps across
two text nodes or a calorie count is glued on with no separator:
  "Tacos -"                (Taco Time)
  "10 Classic Wings860 -"  (Wingstop option label)
  "Small Chips & Salsa+"   (Costa Vida size option)
A mangled name then also fails the later click-by-name lookup, so the add
fails and the voice reply contradicts itself.

Added a shared name-cleaner applied at the boundary of every DOM-scrape
fallback (menu items and option groups). The API paths were already clean, so
this is mostly hardening the fallback - the menu-item "-" shape no longer
reproduces on its own now that DoorDash rewrote the card DOM and the Day 2
server-payload parser supplies clean names.
Verified live: fresh Taco Time (40 items) and Costa Vida (22 items) scrapes
have zero mangled names; Costa Vida "Chips & Salsa" -> "Size" -> "Small Chips
& Salsa" adds end-to-end into the real cart at $4.49. 24 unit cases pass.

QUANT TRADING SYSTEM - new project, started Sun Sep 7
(separate repo and plan - included here as it's the same reporting week)

TIME: ~3.5 h, one session (Sun Sep 7) - estimate. Covers the full phased
plan, a shareable plan page, and Phases 0 + 1.

A learning-first quant trading system in Python, built in 7 gated phases
(0-6): data pipeline -> honest backtester -> trained model -> a math + crypto
agent ensemble -> paper trading -> a gated ~$100 real-money test. The point
is fluency in data pipelines, simulation, testing and statistical honesty;
profit is secondary. Built around crypto (spot) to avoid market-hours edge
cases. Two phases landed this session.

  Phase 0 - foundations ....................... DONE (v0.0-scaffold, deaed31)
  Phase 1 - data pipeline .................... DONE (v0.1-data, f75c99d)


PHASE 0 - FOUNDATIONS

Tested, runnable skeleton: uv for env/deps, src/quant package, ruff (lint +
format), mypy --strict, pytest, GitHub Actions CI on every push, private repo
pushed. config.py loads typed settings from .env - secrets optional, only

that in. Definition of Done met: a fresh clone passes all four checks and CI
is green.


PHASE 1 - DATA PIPELINE  (31 tests)

src/quant/data/, four modules:
  - schema.sql - OHLCV bars table; composite primary key (symbol, timeframe,
    timestamp_utc) makes a re-fetch an update, not a duplicate.
  - store.py - connect / init_db / upsert_bars (rejects naive timestamps) /
    load_bars (UTC-indexed).
  - fetchers.py - a retry-with-backoff decorator, a pure normalizer that
    absorbs yfinance's version-to-version shape drift, the fetch call, a CLI.
  - quality.py - sanity_check (reports bad OHLC rows) and find_gaps (missing
    days).

Verified live: `python -m quant.data.fetchers BTC-USD --start 2019-01-01`
fetched 2807 daily bars (2019-01-01 -> 2026-09-07), 0 gaps, sanity clean; a
second run left the count at 2807 (idempotent). data/quant.sqlite is
gitignored.
