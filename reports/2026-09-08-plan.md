### Day 1 — Carryover: saved-order record from the real cart (audit #6)

`server.js`'s checkout handlers (`/api/food/checkout` ~3510, voice `[PLACE_ORDER]` ~675)
build the saved order record's **item list** from the local SQLite cart, not the real
DoorDash cart that was just checked out. The 8/31 `cff2d6f` fixed the *totals* (they're
scraped real now) but not the line items — if local and real state had drifted (e.g. a
`REMOVE_ITEM` that only logged a warning), the recorded order won't match what was charged.
Have `checkoutCurrentCart()` return the real cart line items alongside `orderTotals`, and
build `db.createOrder(...)` from those when present. Small, well-scoped.

### Day 3 — SMS: `[SELECT]` not updating `currentRestaurant` on a 2nd select

A second `[SELECT]` in one SMS session doesn't update `prefs.currentRestaurant` (stays on
the first pick until a manual reset) — the SMS `[SELECT]` handler is separate from
`/api/food/select`, which does persist it correctly. Fix the SMS handler to match, then
re-run the first-time-SMS-user flow (fresh number → onboarding → save address → setup
doordash → search → select → **select again** → add) that was blocked here on 8/31.

### Day 4 — SMS: verify the pre-charge confirmation scrape end-to-end (Railway)

The 8/31 `91a596a` SMS pre-charge confirmation feature (preview delivery address + card
last-4 + real total, wait for "confirm") has never been verified against a real
non-dry-run checkout page — the Pi's browser wouldn't load checkout and `DRY_RUN` is on.
Run it on Railway (real checkout page, same one the scrape targets): drive a fresh SMS
order to the confirmation step, confirm the address / card / total in the reply are the
real scraped values, then `cancel` (do **not** place). One real placement only if the
scrape looks right and you want the full loop confirmed.

### Day 5 — `readBrowserCart()` proper fix

live 9/7: `"Chips & SalsaSmall Chips & Salsa, Pico De Gallo$4.491 ×1 ×1 × - $0.00"`.
