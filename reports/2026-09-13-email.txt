DAY 1 - SAVED-ORDER RECORD FROM THE REAL CART  (de404ca, Sep 9)

The checkout handlers built the saved order record's item list from the local
cart instead of the real DoorDash cart just checked out - if the two drifted,
the record wouldn't match what was charged. Now scrapes the checkout page's
real itemized list and builds the record from that, falling back to the local
cart when the scrape is empty. 9 unit cases pass.
NOT verified going in: the checkout-page scrape itself - rode with Day 4.

DAY 3 - SMS SELECT SPLIT-BRAIN  (ed9247a, Sep 9, verified live)

A second SELECT in one SMS session didn't update the current restaurant - the
SMS handler only wrote it on menu-load success, while the cache write only ran
on scrape success, so a failed 2nd select left the two disagreeing and later
adds hit the wrong restaurant. Fixed to persist both together the moment the
selection resolves, matching the touchscreen handler. Verified both success
and scrape-fail cases live.


DAY 4 - PRE-CHARGE SCRAPE VERIFICATION: BLOCKER FOUND AND FIXED, NEW ONE HIT

Sep 11: deployed to Railway, hit two new bugs before reaching a checkout
preview - extractMenuItems() returned 0 items for every restaurant tried, and
Claude sometimes skipped the real SELECT command on a retry and hallucinated a
fake menu instead. Paused, nothing charged.

Sep 13 - ROOT-CAUSED AND FIXED THE 0-ITEMS BUG. Added a diagnostic dump for
the specific case where prices are detected but extraction finds nothing,
deployed, reproduced immediately. The dump caught it: the page was DoorDash's
logged-out marketing HOMEPAGE, not the store page - despite the URL bar
showing the store URL correctly. Traced to a race: the SMS/voice select
handler fired clearBrowserCart() WITHOUT awaiting it, immediately before
extractMenuItems(). clearBrowserCart() internally navigates the shared browser
page to /home to reach the real cart drawer; extractMenuItems() isn't
serialized against it, so it sometimes read /home mid-navigation instead of
the store page. Explained every symptom: identical page height across
different restaurants (home is always the same page), "prices detected" (from
home's own promo banner), 0 real items.
FIXED by deferring the cart-clear until after menu extraction completes.
VERIFIED LIVE: the exact restaurant that returned 0 items twice before the fix
returned a real, correct 108-item menu right after, from a fresh select.

Also confirmed the Claude-hallucination bug is WORSE than documented - it
fired on fresh first-try selects today (3 for 3 on one test number), not just
retries as previously thought. Makes SMS unreliable as a test tool on its own;
real verification now needs the kiosk API or a log check for a real SELECT
line. Still open, needs a system-prompt fix.

New minor finding: a fresh search can resolve SELECT against a stale cached
search-results list from an earlier query. Not investigated yet.

THROUGH-LINE: nothing has an edge, and that's the honest finding, not a
failure. SMA doesn't beat buy-and-hold; the trained model is worse than a
coin flip; the agent ensemble's apparent win is explained by trading only
6.3% of the time on a below-chance rule agent during a bad BTC stretch -
suppressing losses by barely trading, not finding signal.

PHASE 2 - bar-by-bar backtester, fills at the next bar's open, costs on by
default, a lookahead cheat-test confirms the strategy interface structurally
can't see the future. Baseline: buy-and-hold +1958%/-77% drawdown vs.
sma_cross +1286%/-59% - the SMA trades return for a calmer ride, no real
edge. Three real bugs found and fixed in a deep math review (a silent NaN
corrupting the portfolio, duplicate-timestamp rows accepted, wrong Sharpe
annualization).

PHASE 3 - trained classifier, 13 features, rolling walk-forward. Holdout
ROC-AUC 0.48 - BELOW CHANCE. As a strategy: -6.9%/-38% drawdown, losing to
buy-and-hold while churning fees. Correctly calls the real-money gate a
no-go on this evidence.

PHASE 4 - agent ensemble (sandboxed tools clipped to the current bar, an LLM
math agent restricted to numeric-only tools so it stays backtestable, a
deterministic rule agent, a consensus gate requiring unanimous long +
confidence). Evaluated: ensemble +0.5%/-5.4% vs. buy-and-hold -4.3%/-53.1% -
beats it on paper, but the gate only went long 33 of 521 times (~94% cash)
and the rule agent's own hit rate on those was 0.455, below chance. Written
up, tagged, pushed, CI green.
