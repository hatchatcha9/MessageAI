### Day 3 — SMS `[SELECT]` split-brain ✅ (`ed9247a`)
Root cause: the SMS `[SELECT: N]` handler only wrote `prefs.currentRestaurant`
inside the menu-load success branches, only `cacheCurrentRestaurant()` on the
scrape path's success branch, and reverted `currentRestaurant` to null on an
empty menu. So a 2nd select whose menu scrape failed left `prefs` on the new
pick while `getCachedCurrentRestaurant()` still returned the old one — later
`[ADD_ITEM_NUM]`s landed on the previous restaurant. Reproduced live on the Pi
via `/api/message` (`prefs=157395/Cafe Rio` vs `cache=157397/Costa Vida`).
Fix: persist `prefs` + `cacheCurrentRestaurant` together the moment the
selection resolves, before the menu load; drop the null revert. Mirrors
`/api/food/select`. Verified both fast-path and scrape-fail 2nd selects — no
split brain either way.

Picked back up the two open items above. Findings, in order:

**1. Root-caused and fixed `extractMenuItems()` returning 0 items** (`37ffe6d`
diagnostic, `057381c` fix). Added a targeted diagnostic dump to
`extractMenuItems()` for the specific case where prices are detected but
extraction finds nothing, deployed, and reproduced live on Railway
immediately (Dave's Hot Chicken, fresh select, 0 items). The dump caught the
real page content: `document.title` was DoorDash's generic homepage title and
the body was pure logged-out marketing copy ("$0 DELIVERY FEE ON FIRST
ORDER... Become a Dasher... Become a Merchant") — not the store page at all,
despite `page.url()` correctly showing the store URL. Traced this to a race:
`server.js`'s SMS/voice restaurant-select handler fired
`doordash.clearBrowserCart()` **unawaited** immediately before
`doordash.extractMenuItems()`. `clearBrowserCart()` is `locked()` (serialized
against other locked ops) but internally does `page.goto('https://www.doordash.com/home')`
to open the real cart drawer; `extractMenuItems()` is exported **unlocked**,
so it doesn't wait for that navigation and can end up reading `/home` instead
of the store page mid-navigation. This explained every symptom precisely:
identical page height across different restaurants (home is always the same
page), "prices detected" (from home's own promo banner, not menu prices),
and 0 real items. Confirmed fixed live: the exact restaurant that returned 0
items twice before the fix (Dave's Hot Chicken) returned a real, correct
108-item menu immediately after, from a fresh select. Checked every other
`extractMenuItems()` call site in `server.js` — none had the same ordering
bug (`[REORDER]` already awaits `clearBrowserCart()` first; the kiosk
`/api/food/select` handler already calls `extractMenuItems()` before its own

## Day 5 continued — 2026-09-13: found the real root cause of the Day 4 blocker too, fixed it, verification interrupted by rate-limiting

Started Day 5 (`readBrowserCart()` parser fix). Never got there — every attempt
failed one step earlier, at "no cart icon found on `/home`" (added a candidate
dump, `0e54fbf`; found zero cart-ish elements at all, `ec304b5`). `/home`
looked like DoorDash's anonymous marketing homepage even right after a
verified-successful login — the same symptom as Day 4's checkout blocker.
That match was the lead worth chasing.

**Root cause, confirmed by a real diagnostic dump (`8f3b017`):** `login()`'s
2FA wait loop was built to auto-read the code from a Windows notification
database via `powershell.exe` — impossible on Railway's Linux container or
the Pi. Once the code input disappeared for *any* reason, the loop
unconditionally declared success (`2FA screen gone - checking login
status...` followed by no actual check). The dump showed why the input kept
disappearing immediately: DoorDash's real verification screen is six
`<input type="number" autocomplete="one-time-code">` boxes with no
name/placeholder — the loop's *ongoing* "is the screen still up" check used a
different, narrower selector list that never included
`autocomplete="one-time-code"` at all, so it always missed them and declared
the screen gone on the very first poll, even while it was genuinely still
sitting there waiting for input. Same gap existed in the code-entry step's
box selector. **This selector mismatch — not a Windows-vs-Linux platform
issue — is why every "verified successful" real login this project has ever
reported was very likely never a real password+2FA login at all**, just
whatever the auto-imported `DOORDASH_COOKIES` session already allowed
(enough for store-page browsing, not enough for `/home` or checkout).

Fixed in stages, each confirmed live before moving on:
1. `37ffe6d`→`613bd7e`: replaced "field disappeared = success" with a real
   check (`verifyRealLoginSuccess()`, forces `/home`, checks for the specific
   anonymous-homepage fingerprint) — first version still used
   `isLoggedIn()`'s cookie signal and gave a false positive live (a session
   cookie is set on the anonymous homepage too); tightened to the homepage's
   own fingerprint text, which held up.
2. `a2b73f9`: fixed the actual selector mismatch (added
   `autocomplete="one-time-code"` to both the ongoing-screen check and the
   code-entry box selector, unified into one shared list). Confirmed live:
   the loop went from exiting instantly to correctly running all 45 attempts
   (~3 minutes), honestly reporting `2FA_TIMEOUT` instead of a false success.
3. Since the code can only ever arrive by real SMS to a human's phone (not
   anywhere this process can read), built a manual relay:
   `doordash.submitVerificationCode()` / `isAwaitingVerificationCode()`,
   reachable via `POST /api/doordash/2fa-code` or a plain 6-digit SMS reply
   (`3aa8a91`).
4. **Found and fixed a real deadlock** (`adc59e5`) before it could bite in
   production: the 6-digit-code intercept lived inside `_handleMessage`,
   which runs behind `withUserLock` (strictly sequential per phone number).
   The `[SETUP_DOORDASH]` message that triggers `login()` is very likely
   still in-flight *holding that exact phone number's lock* while awaiting
   that exact code — a code reply from the same number would queue behind it
   and never be processed, hanging both forever. Moved the intercept above
   the lock, into `handleMessage`.
5. **Fixed the missing user-facing explanation.** `[SETUP_DOORDASH]` gave no
   indication a code might be needed — a first-time user would have no idea
   to expect a text or that replying with digits does anything.
   `login()` now takes an `onAwaitingCode` callback, fired the instant
   DoorDash actually asks for a code (not just after the whole thing times
   out); the SMS handler uses it to proactively text the user what's
   happening and what to do. Also fixed the outer `Promise.race` timeout
   (90s, shorter than the ~3 min wait it now races against) and the
   failure-message hint that used to (wrongly) say this sign-in method
   "isn't supported here yet."

**Partial live confirmation, not fully closed:** the loop demonstrably waits
correctly now and no longer false-positives (`2FA_ABANDONED`/`2FA_TIMEOUT`
both correctly reported when no real code arrived in time). One real code
*was* submitted successfully via the relay (`{"success":true}` from the
